# Gate 4 — task_validation (독립 수용 관찰)

- **대상**: 태스크 frontmatter의 `acceptance_criteria` 전부, 화면 태스크의 DESIGN §5 시각 기준
- **누가**: 그 태스크를 구현하지 않았고 구현 대화를 상속하지 않은 **별도 세션**. 아래 수단 중 하나를 쓰고, 실제 선택은 `loop_setup/LOOP.md`가 정한다.

  | 수단 | 독립성 | 확인 상태 |
  |---|---|---|
  | Orca 워커(새 Claude 세션, 별도 워크트리나 같은 저장소 읽기) | 비상속 | `orca status` ready 확인(2026-11-02). 워커 생성 시험은 loop-setup에서 한다 |
  | `claude -p "<인계서>" --model opus`(`--resume`·`--continue` 없음) | 비상속 | CLI 2.1.316 존재, `-p`·`--max-budget-usd`·`--allowedTools` 옵션 확인 |
  | Claude Code Agent 도구의 새 `general-purpose` 에이전트 | 비상속(새 맥락) | 이 세션에서 사용 가능 |
  | ~~Agent `fork`~~ / 같은 세션에서 역할만 바꾸기 | **상속 → 독립 검증 아님** | 사용 금지 |

- **인계 입력**: `node harness_setup/scripts/task-brief.mjs <태스크ID> <기준 커밋>`의 출력만 넘긴다.
  - 들어 있는 것: 요구·수용 기준·설계 참조·실행 방법·코드 식별·허용 데이터·예산
  - 넘기지 않는 것: STATE/LOG 전체, 구현자의 자체 판정
- **검증자 규칙**: 인계서의 "규칙" 절을 따른다.
  - 제품 코드·테스트·기준·단언을 수정하지 않는다.
  - 코드를 읽기만 하고 판정하지 않는다. 실제 실행·관찰로 판정한다.
  - 임시 데이터만 쓰고, 실제 API 키를 쓰지 않는다.
- **순서**: lint → unit → e2e가 같은 코드 상태(커밋 해시가 같고 미커밋 변경이 없음)에서 PASS한 뒤에만 시작한다. 검증자도 게이트를 직접 다시 돌려 확인한다.
- **반환·보존**
  - 반환 내용: 기준별 PASS/FAIL/판정 불가, 관찰 증거, 재현 방법
  - 원문 보존 위치: `harness_setup/evidence/<태스크ID>/validation-<시각>.md`
  - LOG 기록: 요약과 경로
- **판정**
  - 모든 기준이 PASS일 때만 태스크를 `completed`로 바꾼다.
  - FAIL이 있으면 구현 단계로 되돌린다. 수정하면 이전 게이트 결과가 무효가 되므로 lint부터 다시 돌린다.
  - 판정 불가(환경 문제)는 원인을 해소한 뒤 다시 검증한다. 통과로 세지 않는다.
  - 검증자가 무언가 직접 고쳤다면, 그 변경은 다른 검증자가 다시 판정한다.
- **묶음 검증**
  - 같은 커밋에서 여러 태스크를 한 검증자가 볼 수 있다.
  - 이때도 태스크마다 기준별 표를 따로 채운다. 하나의 PASS로 여러 태스크를 닫지 않는다.
- **상태**
  - **절차와 인계서 스크립트는 활성**(2026-11-02 실행 확인: `task-brief.mjs phase-03-task-01` 출력 정상, 잘못된 ID에는 종료 코드 2)
  - **제품 판정은 아직 없음**: 대상 코드가 없다.
