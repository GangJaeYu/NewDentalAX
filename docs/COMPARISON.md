# 단일 프롬프트 vs 플러그인(하네스·루프) — 같은 요구서, 다른 결과

> 처음으로 → [README](../README.md) · 만든 과정 → [BUILD_STORY](BUILD_STORY.md)

두 저장소는 **같은 요구서**에서 출발했습니다([요구서 원문](prompts/prompt.md#3-요구서-원문)).

- **단일 프롬프트판**([GangJaeYu/DentalAX](https://github.com/GangJaeYu/DentalAX)): 요구서를 새 세션에 한 번 넣었고, 이후 AI가 혼자 계획·개발·테스트·문서화를 했습니다. 대부분의 "바이브 코딩"이 이 방식입니다.
- **플러그인판(이 저장소)**: 같은 요구서를 `harness_loop_fullstack_kor` 플러그인 절차에 태웠습니다. 순서는 요구 ID·수용 기준 → 설계 → 37개 태스크 → 검증 하네스 → 구현 루프 → **별도 세션 독립 검증**입니다.

결론부터 말하면, **단일 프롬프트판은 빠르고 기본기가 좋은 시제품**입니다. 플러그인판은 **"됐다"는 말을 증거로 확인하고 출시 전에 결함을 잡는 체계**를 갖춘 상용 후보입니다. 차이는 코드를 짠 AI의 실력보다 **검증 구조**에서 나옵니다.

## 2. 왜 "검증 구조"가 상용 여부를 가르나

AI는 자기가 만든 코드를 자기가 테스트하면, **자기가 생각한 경우만** 시험합니다. 그래서 "테스트 통과 = 완료"가 되어도, 사용자가 실제로 겪을 상황(한글 Windows 새 창, 다른 프로그램이 쓰는 포트, 태블릿 폭, 서버 오류 응답)은 빠지기 쉽습니다.

플러그인판은 이 빈틈을 구조로 막습니다.

1. **수용 기준을 먼저 씁니다**(PRD). "관찰 가능한 문장"이라서 나중에 누가 봐도 합격·불합격을 가를 수 있습니다.
2. **게이트를 건너뛸 수 없습니다**. lint → unit → e2e 순서이고, 테스트 0건·건너뜀·흔들림이 있으면 불합격입니다(`harness_setup/scripts/gate.mjs`).
3. **만든 AI와 판정하는 AI를 나눕니다**. 검증자는 구현 대화를 넘겨받지 않은 새 세션입니다. 요구·수용 기준·실행 방법만 받고, 기준마다 직접 재현한 증거를 남깁니다.
4. **불합격이면 고치고 다시 검증합니다**. "부분 통과"도 남은 기준을 따로 재검증하기 전에는 완료로 치지 않습니다.
5. **모든 결정과 사고를 기록합니다**([DECISIONS](DECISIONS.md) 100여 건, [LOG](../plan_setup/LOG.md)). 나중에 다른 사람이나 AI가 이어받을 수 있습니다.

이 구조가 실제로 잡아낸 결함은 [BUILD_STORY "독립 검증이 잡은 문제"](BUILD_STORY.md#독립-검증이-잡은-문제-만든-ai는-됐다고-보고했던-것들)에 있습니다. 모두 **구현한 AI가 이미 자기 테스트를 통과시키고 "완료"라고 보고한 뒤에** 발견된 것들입니다.

## 3. 단일 프롬프트판 점검 결과

- **점검 방법**: 단일 프롬프트판 코드(커밋 `원 프롬프트(아이디어)를 원문 그대로 교체`, 2026-10-16)를 읽어서 확인했습니다. 내려받은 코드를 실행하지는 않았습니다.

### 재현 실험 (항목 1)

단일 프롬프트판 코드가 아니라 같은 조건만 만든 짧은 실험입니다. 이 PC(Windows 11, Node 24)에서 실행했습니다.

```js
const net = require('net');
const a = net.createServer().listen(18365, '::', () => {          // 다른 프로그램이 IPv6로 포트 사용
  const b = net.createServer();
  b.on('error', (e) => console.log('충돌 감지:', e.code));
  b.listen(18365, '0.0.0.0', () => console.log('0.0.0.0 listen 성공 — 충돌을 알려 주지 않음'));
});
// 출력: 0.0.0.0 listen OK although [::]:18365 is taken (no EADDRINUSE)
```

### 단일 프롬프트판의 장점 (공정하게)

- **빠릅니다**: 1시간 45분, 사람 개입 0회로 대부분의 기능이 동작합니다. 아이디어 검증이나 시제품에는 이만한 것이 없습니다.
- **가볍습니다**: 실행 외부 부품이 express 1개이고 빌드 단계가 없습니다(Preact + htm). 코드를 읽고 고치기 쉽습니다.
- **보안 기본기가 좋습니다**: CSP, CSRF 토큰 + Origin 확인, HttpOnly·SameSite=Strict 쿠키, scrypt, 로그인 잠금, 매개변수 SQL을 갖췄습니다. 화면은 innerHTML을 쓰지 않고, AI로 보내는 모든 메시지(원내 문서 문맥 포함)에 개인정보 필터를 겁니다. 점검하면서 SQL 인젝션·XSS 결함은 찾지 못했습니다.

## 4. 그래서 무엇을 쓰면 되나

| 목적 | 추천 |
|---|---|
| "이런 게 되나?" 아이디어 확인, 시연용 시제품 | 단일 프롬프트 |
| 원내에서 **매일** 쓰고, 직원 여럿이 다양한 기기로 접속하고, 데이터·키·개인정보를 맡기는 서비스 | **플러그인(하네스·루프)** |
| 나중에 다른 사람·다른 AI가 이어서 고쳐야 하는 서비스 | **플러그인**: 요구 ID·결정 기록·태스크·검증 증거가 남음 |

플러그인판이 시간을 더 쓴 이유는 대부분 **검증과 재검증**입니다. 그 시간 동안 잡은 결함은 하나하나가 "원장님이 더블클릭했는데 안 열린다", "태블릿에서 경고가 잘린다", "대화 기록에 주민번호 앞자리가 남는다" 같은, 현장에서 신뢰를 잃는 종류였습니다.
