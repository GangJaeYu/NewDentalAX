## 측정 명령

```
npm run perf
# = node scripts/perf.ts  (기본: --rounds 3 --count 100 --duration 60 --connections 20 --screens 5 --scale 10, 포트 PERF_PORT=18190)
```

- 작업 사본 안 `.tmp/perf/run-<시각>/`에 데이터를 만들고 끝나면 지운다. 실제 `data/` 폴더와 8090 포트는 쓰지 않는다.
- 세 가지를 한 회차로 묶어 **3회** 재고, 항목마다 **가장 나쁜 값**으로 판정한다.
  1. 주요 목록 API: 화면이 처음 열릴 때 부르는 주소(쪽 크기·기본 필터 포함)를 API마다 100번 차례로 부른다(준비 운동 1번 제외). 실제 로그인 세션, 실제 HTTP.
  2. 동시 연결: autocannon, 연결 20개 × 60초, 생각 시간 없이 대시보드(×3)·알림 요약(×2)·재고·입출고·발주서·공지·지출·감사 로그·도우미 기록을 돌아가며 부른다. 시간 초과 10초. 오류 = 연결 오류 + 2xx가 아닌 응답 + 시간 초과.
  3. 첫 화면: 로그인 화면에서 "로그인" 단추를 누른 때부터 대시보드가 다 그려질 때까지(카드 10개 제목이 모두 보이고, 서버 날짜가 머리말에 들어가고, "불러오는 중"이 사라짐), 그리고 로그인한 상태로 새 탭에서 주소 `/`를 열어 다 그려질 때까지. 회차마다 5번씩.
- 회차 직전 PC CPU가 50%를 넘으면 15초씩(최대 8번) 기다린다. 재는 동안 PC 평균 CPU가 65%를 넘은 회차는 다른 작업과 겹친 것으로 보고 기록을 남긴 채 다시 잰다(회차마다 최대 3번).
- 결과 원본: `harness_setup/evidence/phase-05-task-01/perf-2026-11-02T23-28-33-487Z.json`(전체 수치), `.txt`(표), `npm-run-perf-output.txt`(명령 출력 전체).
- 같은 내용의 자동 검사: `scripts/perf-lib.test.ts`(unit, 10배 데이터에서 API p95·짧은 동시 연결 오류 0), `tests/e2e/perf-first-screen.spec.ts`(e2e, 10배 데이터 첫 화면 2초 이내).

### 다른 작업과 겹친 앞선 측정(판정에서 뺀 기록, 투명성을 위해 남김)

같은 날 먼저 한 측정(재는 동안의 CPU 관찰을 넣기 전, 원본 `harness_setup/evidence/phase-05-task-01/perf-2026-11-02T23-17-08-768Z-disturbed-FAIL.txt`)에서는 1·2회가 통과(오류 0, p99 1,246·1,339ms)했지만, **3회에서 동시 연결 요청이 541건(초당 9)으로 떨어지고 시간 초과 1건(10초)** 이 나왔다. 그때 같은 PC에서 다른 작업 사본 4곳의 E2E 검사(`gate.mjs e2e`)와 수동 검증 서버가 함께 돌고 있었다(프로세스 목록으로 확인, 직후 CPU 51%).

- 서버 쪽 원인이 아닌지 확인: 같은 데이터로 서버를 띄워 20초 부하를 6번 잇달아 걸었더니 처리량(초당 28~36)·서버 메모리(251~259MB)·WAL 크기(4MB)가 그대로였다. 회차가 거듭될수록 느려지는 누수·쌓임은 없었다.
- 그래서 측정 절차에 "재는 동안의 PC 평균 CPU 기록, 65%를 넘으면 그 회차를 다시 잼"을 넣고 다시 쟀다(위 결과). 다시 잰 측정에서는 판정에서 뺀 회차가 없었다.

### 관찰(기준 안이지만 알아 둘 것)

- 가장 무거운 API는 대시보드(약 90~115ms)와 재고 목록(약 50~60ms)이다. 둘 다 품목별 현재고·유효기간(FEFO)·단가를 입출고 6만 건에서 한 번에 계산한다(database.md §3.2, `GROUP BY item_id` 한 번 + 품목별 계산). N+1 조회는 없었다.
- 서버는 프로세스 1개라 요청을 차례로 처리한다. 생각 시간 없이 20개 연결이 계속 부르면 응답이 줄을 서서 p99가 1.3~2초가 된다(오류는 0). 실제 직원 20명은 화면을 보며 쉬는 시간이 있어 이보다 가볍다.
- 개선 여지(이번에는 하지 않음): `stock_moves (item_id, type, qty)`·`stock_moves (moved_at, id)` 색인을 시험 삼아 붙이면 대시보드 약 102→78ms, 입출고 기록 약 42→23ms로 줄었다. 기준을 이미 넉넉히 넘어서 공유 파일(마이그레이션, 090~ 예비 번호)을 건드리지 않았다.
