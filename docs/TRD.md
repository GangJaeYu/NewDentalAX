## 1. 기술 결정 (TD)

### TD-001 런타임: Node.js 24 LTS 하나만 쓴다 — 확정
- **근거**
  - NFR-003: 비개발자 30분 설치, 오프라인 실행
  - 원문 9절: Windows 안정, 대중적 기술, 의존성 최소
  - 개발 PC에서 Node 24.13.0 동작을 확인함
- **선택**: 서버, 빌드, 테스트를 모두 Node 24로 한다. README에서 Node.js 24 LTS 설치 파일(.msi)을 클릭 단위로 안내한다. `start.bat`은 메이저 버전이 24 미만이면 한국어로 안내하고 멈춘다.
- **대안**
  - Python(FastAPI): 설치와 PATH 문제가 비개발자에게 더 어렵고, 프론트엔드 도구는 결국 Node가 필요하다.
  - Electron이나 설치형 exe: 패키징과 서명이 복잡하고 업데이트가 어렵다.
- **되돌리기 비용**: 큼(전체 스택).
- **확인 방법**: 깨끗한 폴더에서 README 절차를 그대로 따라 `start.bat`을 실행하는 최종 통합 검증(NFR-003).

### TD-002 언어: TypeScript, 서버는 빌드 없이 실행 — 확정
- **근거**
  - 유지보수를 Claude Code로 맡기므로 타입 정보가 수정의 안전성을 높인다.
  - Node 24.13은 `.ts` 파일을 경고 없이 바로 실행한다(실험으로 확인함).
- **선택**
  - 서버는 Node 타입 제거 방식으로 바로 실행하고, "지울 수 있는 문법"만 쓴다(`enum`, `namespace`, 매개변수 속성 금지, import에 `.ts` 확장자). `tsconfig`에 `erasableSyntaxOnly`와 `verbatimModuleSyntax`를 둔다.
  - 화면 코드는 Vite로 빌드한다. 빌드 결과물 `web/dist`는 저장소에 포함해서 사용자 PC에서는 빌드할 필요가 없게 한다.
- **확인 방법**: 린트 게이트 `tsc --noEmit`(서버·화면), `start.bat`이 빌드 없이 실행되는지.

### TD-003 DB: `node:sqlite` 단일 파일 — 확정 (위험 관리 포함)
- **근거**
  - NFR-004: 단일 파일, 파일 복사로 백업
  - 원문 9절
  - 실험 결과: SQLite 3.50.4, FTS5, `VACUUM INTO`, `backup()`이 동작함
- **선택**
  - `data/app.db`를 WAL 모드로 쓰고, 외래키를 켠다.
  - 스키마는 `server/db/migrations/NNN_*.sql`로 관리하고 `schema_version` 테이블로 순서대로 적용한다.
  - 모든 SQL은 prepared statement와 매개변수 바인딩만 쓴다(NFR-002 AC3).
  - 실험 단계 경고는 `--disable-warning=ExperimentalWarning`으로 숨긴다.
- **대안**: `better-sqlite3`는 네이티브 모듈이다. 미리 빌드된 파일이 없는 Node 버전에서는 Visual Studio 빌드 도구가 필요해서 비개발자 설치가 실패할 위험이 크다. 그래서 고르지 않았다.
- **위험**: `node:sqlite` API가 아직 "실험" 표시다. 모든 DB 접근을 `server/db/index.ts` 래퍼 한 곳으로 모아서 바뀌어도 한 파일만 고치면 되게 한다. Node 메이저 버전은 24로 안내한다.
- **확인 방법**: 마이그레이션·백업 통합 테스트. NFR-005 부하 측정에서 품목 1,000개·입출고 2만 건 기준 p95 300ms 이하.

### TD-006 인증·세션·CSRF — 확정
- **근거**: FR-001~003, NFR-002, 사용자 결정(미사용 8시간 만료, 5회 실패 시 15분 잠금).
- **선택**
  - 비밀번호
    - `node:crypto` scrypt(N=2^15, r=8, p=1, 솔트 16바이트)로 해시한다. 비교는 `timingSafeEqual`로 한다.
    - 의존성이 없고 OWASP 권장 KDF 중 하나다.
  - 세션
    - 서버 쪽 `sessions` 테이블에 무작위 32바이트 토큰의 SHA-256 해시를 저장한다.
    - 쿠키는 `HttpOnly; SameSite=Strict; Path=/`이고, http라서 `Secure`는 붙이지 않는다(TD-017).
    - 요청이 올 때마다 만료를 8시간 뒤로 미룬다.
  - 로그인 잠금: 아이디별 연속 실패 5회면 15분 잠근다. 같은 IP에서 짧은 시간에 많이 실패하면 추가로 제한한다.
  - CSRF
    - 세션마다 토큰을 두고, 상태를 바꾸는 요청은 `X-CSRF-Token` 헤더가 필요하다.
    - 동시에 `Origin`/`Host`가 일치하는지도 검사한다.
  - 첫 실행: 사용자가 0명일 때만 `/api/setup`이 열린다. 트랜잭션 안에서 다시 확인해서 동시 요청을 막는다.
  - 테스트 시간 조작: 세션·잠금 계산은 주입 가능한 `clock`을 쓴다(FR-002 AC3 테스트).
- **확인 방법**: 통합 테스트(잠금, 만료, 로그아웃 후 401, CSRF 없음 403, 평문 비밀번호 없음).

### TD-007 보안 헤더·원내망 제한 — 확정
- **근거**: NFR-002 AC4, FR-009, 원문 7절.
- **선택**
  - 보안 헤더
    - CSP는 `default-src 'self'; img-src 'self' data: blob:; style-src 'self'; script-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'`로 둔다.
    - 그 밖에 `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cross-Origin-Opener-Policy: same-origin`을 붙인다.
  - 원내망 제한
    - 요청 출발지가 사설망(10/8, 172.16/12, 192.168/16, 169.254/16, IPv6 ULA·링크로컬)이나 루프백이 아니면 403을 돌려준다.
    - `data/config.json`의 `allowExternal: true`로 끌 수 있고, 그 위험은 README에 적는다.
  - 서버는 `[::]:8090`(이중 스택, IPv6를 쓸 수 없으면 `0.0.0.0`)에서 기다린다. 열기 전에 `::`·`0.0.0.0`·`127.0.0.1`·`::1`·원내 IP에서 포트가 비었는지 확인한다. Windows는 주소가 정확히 같을 때만 충돌을 알려 주기 때문이다(01-01 시도 3, 실험으로 확인). 최종 판정은 연 뒤의 자기 확인(실행 표식 X-Instance 대조)으로 한다(01-01 시도 4). 포트와 host는 설정으로 바꿀 수 있다.
- **XSS**
  - React의 기본 이스케이프를 쓰고 `dangerouslySetInnerHTML`을 금지한다(린트 규칙).
  - 마크다운 미리보기는 HTML을 허용하지 않는 자체 변환기로 만든다.
- **확인 방법**: 헤더 검사 테스트, 외부 IP를 흉내 낸 요청에 403, XSS 문자열이 저장된 뒤에도 실행되지 않는지 확인하는 E2E.

### TD-008 비밀값 저장(API 키) — 확정
- **근거**: FR-031.
- **선택**
  - API 키는 AES-256-GCM으로 암호화해서 DB에 저장한다.
  - 암호화 키는 첫 실행 때 만든 `data/secret.key`(32바이트)에 둔다.
  - 백업에는 DB와 함께 `secret.key`도 넣는다. 다른 PC로 복원해도 키를 다시 입력할 필요가 없게 하기 위해서다. 그 대신 백업 폴더를 원내 PC 밖으로 내보낼 때 주의하라고 README에 적는다.
  - API 응답에는 `maskedKey`(끝 4자리)만 내려준다.
- **확인 방법**
  - 테스트로 모든 API 응답 JSON과 HTML에서 저장한 키 문자열을 검색해 없음을 확인한다.
  - 로그에도 키가 없는지 같은 방식으로 확인한다.

### TD-009 LLM 연동: 공급자 어댑터(직접 HTTP) — 확정 (요청 형식 세부는 구현 때 공식 문서로 재확인)
- **근거**: FR-030~037, NFR-008, 원문 6절.
- **선택**
  - 어댑터 구조
    - `server/ai/providers/{anthropic,openai,gemini,demo}.ts`가 같은 인터페이스 `generate({system, messages, images?, maxTokens, stream}) → {text, usage, stream?}`를 구현한다.
    - SDK 없이 `fetch`로 호출한다. 의존성을 최소화하고, 테스트용 가짜 서버로 base URL을 바꾸기 쉽게 하기 위해서다.
  - 공급자별 호출 방식
    - Anthropic: Messages API(`POST /v1/messages`, `x-api-key`, `anthropic-version` 헤더)
    - OpenAI: Responses API(`POST /v1/responses`, `store:false`). 2026-11-02 공식 문서로 확인했다(OQ-009, 02-02).
    - Gemini: `generateContent`/`streamGenerateContent`
    - 구현할 때 각 공식 API 문서로 요청·응답·사용량 필드를 다시 확인하고 DECISIONS.md에 기록한다.
  - 모든 AI 호출은 `server/ai/gateway.ts` 한 곳을 지나간다. 이 게이트웨이가 차례로 처리하는 일:
    1. 기능이 켜져 있는지, 역할이 허용되는지 확인
    2. 예산 확인
    3. 개인정보 필터(TD-010)
    4. 모델 등급을 실제 모델로 바꾸기
    5. 시간 초과(AbortController)
    6. 오류를 한국어 안내로 바꾸기
    7. 사용량·비용 기록
    8. 응답 필터
  - 스트리밍: 서버가 공급자의 스트림을 받아 브라우저에 SSE로 다시 보낸다(FR-060 AC4). 사용자가 멈추면 공급자 요청도 끊는다.
  - 비용
    - 계산식: `(입력 토큰 × 입력 단가 + 출력 토큰 × 출력 단가) / 1,000,000 × 환율`
    - 입력 토큰이 일정 수를 넘으면 가격이 바뀌는 모델은 단가 표의 구간으로 처리한다.
    - 공급자가 사용량을 주지 않으면 글자 수로 추정하고 "추정"으로 표시한다.
  - 데모 모드: 키가 없거나 공급자가 `demo`이면 기능별 예시 응답을 돌려준다. 스트리밍도 흉내 내고, 사용량은 0원·"데모"로 기록한다.
- **대안**: 공식 SDK 세 개를 쓰면 의존성과 버전 관리 부담이 커지고, 가짜 서버로 테스트하기 어렵다.
- **확인 방법**: 가짜 HTTP 서버 통합 테스트(공급자별 요청 형식, 사용량 파싱, 429·401·시간 초과·5xx 안내 문구). 실제 공급자 호출은 하지 않는다(OQ-006).

### TD-010 개인정보 필터 — 확정
- **근거**: FR-032, NFR-001, 원문 4절.
- **선택**
  - 순수 함수 모듈 `server/privacy/filter.ts`로 만든다. 감지 대상과 방법:
    - 주민·외국인등록번호: 앞 6자리가 날짜로 유효한지 + 7번째 자리
    - 휴대·일반 전화번호: 지역번호 목록 기반
    - 이메일
    - 카드번호: 13~19자리 + Luhn 검사로 오탐을 줄임
    - 계좌번호: 하이픈이 있는 은행 계좌 형식 + "계좌" 문맥
    - 여권번호
  - 처리
    - 결과는 `{redactedText, findings[{type, count}], blocked}`로 돌려준다.
    - 기본 정책은 주민번호·카드번호는 차단, 나머지는 가리기다.
    - 병원 대표번호 같은 허용 목록은 가리지 않는다.
  - 브라우저에도 같은 규칙의 가벼운 사본을 두어 입력 중 경고를 띄운다(시안과 동일). 판정은 서버가 최종으로 한다.
- **확인 방법**

  - 오탐 대조 세트: 날짜(2026-11-02), 금액(1,234,000원), 발주번호(PO-2611-003), 로트 번호, 사업자번호

    - 상위 6개를 쓴다.
