## 4. 배정 규칙

1. **고르기**: `depends_on`이 모두 `completed`(독립 검증까지 끝남)이고 차단이 없는 태스크를 고른다. 순서는 phase 번호, 그다음 PLAN.md §2 묶음을 따른다.
2. **상한**
   - 구현 워커는 동시에 4개까지 둔다.
   - 무거운 작업(e2e·스크린샷·perf·`npm ci`)은 워커 지시문에서 동시 2개까지로 제한한다.
   - 메모리 사용률이 85%를 넘거나 워커 시작이 실패하면 신규 배정을 줄인다. 최소 1개까지 줄인다.
   - 01-01 → 01-04는 직렬로 1개씩 한다.
3. **슬롯과 포트**
   - 구현 슬롯 k(0~3): `E2E_PORT=18090+k`
   - 검증 슬롯 k: `E2E_PORT=18094+k`
   - 수동 서버: `PORT=18190+k`
   - DATA_DIR은 항상 작업 사본 안의 임시 폴더(`.tmp/`, git 제외)다.
4. **소유권**
   - 태스크의 `files`와 PLAN.md §3 공유 파일 규칙으로 정한다.
   - 같은 파일을 만지는 태스크는 동시에 배정하지 않는다.
   - 워커가 범위 밖 공유 파일을 바꿔야 하면 그 변경을 하지 않고 보고에 "변경 요청"으로 남긴다. 조정자가 통합 때 반영한다.
5. **워커 지시문**(조정자가 `--spec-file`로 넘김)에 넣는 것:
   - 태스크 파일 경로
   - `CLAUDE.md`·HARNESS·관련 설계 절
   - 소유 파일·금지 사항
   - `npm ci` 선행
   - 포트 슬롯
   - 게이트 lint → unit → e2e를 직접 통과시킨 뒤 브랜치에 커밋
   - 보고 형식: 커밋 해시, 게이트 결과(gate.mjs 판정과 건수), 수용 기준별 자체 확인, 변경 요청, 미해결
   - 남은 예산
   - 워커는 STATE·LOG·태스크 상태를 고치지 않는다.

## 5. 한 태스크의 순서

1. 조정자가 태스크를 `in_progress`로 바꾸고 STATE에 담당·작업 사본·기준 커밋을 적은 뒤 커밋한다.
2. 구현 워커를 시작하고, 차례를 마쳐 Orca의 알림을 기다린다.
3. `worker_done`을 받으면 보고와 실제 브랜치(커밋 존재, diff 범위)를 대조한다. 늦거나 중복된 보고는 현재 dispatch와 대조해 한 번만 반영한다.
4. **통합**
   - main에 `git merge --no-ff`로 병합한다. 충돌은 조정자가 해결한다.
   - main에서 `npm ci`(잠금 파일이 바뀌었을 때만) → `npm run build:web` → `web/dist`를 커밋한다.
   - `gate.mjs lint/unit`을 돌리고, 화면 태스크면 `e2e`도 돌린다.
   - 실패하면 수정 워커를 배정하거나, 작은 충돌·통합 문제는 조정자가 직접 고친다.
5. **독립 검증**
   - `task-brief.mjs <ID> <병합 전 main>`의 출력을 지시문으로 해서, 병합 커밋 기준 새 작업 사본에 검증 워커를 띄운다.
   - 같은 커밋에 병합된 태스크 여러 개는 검증 워커 하나가 태스크별 표로 함께 볼 수 있다.
6. **판정**
   - 검증 결과 원문은 `harness_setup/evidence/<ID>/validation-<시각>.md`에 저장한다.
   - 모든 기준이 PASS이면 `completed`로 바꾸고, STATE·LOG·PROGRESS를 갱신해 커밋한다.
   - FAIL이 하나라도 있으면 `failed`로 바꾸고 증거를 첨부해 수정 워커를 배정한다(§6). 수정 뒤에는 lint부터 다시 판정한다.
7. 워커를 해제하고 작업 사본과 브랜치를 삭제한다. 자기가 만든 dispatch·브랜치인지 확인한 뒤에만 지운다.
8. **phase 경계**: 소속 태스크가 모두 completed이면 phase 묶음 기준을 main에서 확인한다(필요하면 검증 워커). 결과는 LOG에 남긴다.

## 6. 복구 (질문 없이)

- **실패 분류**: 코드 결함 / 검사·문서 불일치 / 환경(포트·설치·Edge) / 흔들림(flaky) / 판정 불가 / 워커 시작 실패 / 불완전한 결과 / 통합 실패
- **같은 방식은 3회까지**: 같은 방식의 수정이 3회 실패하거나 진전이 없으면 심층 분석으로 넘어간다.
  1. 관찰과 가설을 LOG에 쓴다.
  2. 가설을 가르는 실험을 한다.
  3. 다른 전략을 세워 계속한다.
  - 재실행만 해서 통과시키기, 검사 대상 축소, 기준 낮추기는 새 전략으로 인정하지 않는다.
- **워커 문제**
  - 시작에 실패하면 `failedStage`를 보고 recovery 안내를 따른다. 같은 명령을 그대로 다시 실행하지 않는다.
  - escalation(`stopReason`)이 오면 `send`로 지시하거나, 정지 후 `--retry-of`로 다시 시도한다.
  - 조용하다는 이유만으로 종료하거나 중복으로 실행하지 않는다.
- **사용량 한도(사용자 합의: 대기 후 재개)**
  - 워커가 한도에 닿으면 escalation이 온다. 해당 태스크를 대기 상태로 STATE에 적고 다른 독립 작업을 계속한다. 한도가 풀리면 `send`나 retry로 재개한다.
  - 조정자 세션이 한도에 닿으면 STATE가 이미 최신이어야 한다(전환마다 커밋). 재개는 다음 Orca 알림이나 사용자의 "이어서" 호출로 한다.
  - 자동 재시작은 Orca 알림 경로만 확인했다. 조정자 자체의 자동 재기동은 확인하지 않았다.
- **차단**: 새 사용자 결정이나 권한 없이는 못 하는 태스크와 그 후행만 `blocked`로 두고, 사유와 재개 조건을 적는다. 독립 작업은 계속한다. 질문 파일이나 응답 대기는 남기지 않는다.
- **종료 조건**: 다음 중 하나일 때 최종 미완료 보고로 끝낸다.
  - 24시간 소진
  - 필수 권한이 없고 대안도 없음
  - 분석 뒤에도 실행 경로가 없음
- **24시간에 닿으면**
  1. 신규 배정을 멈춘다.
  2. 자기 워커를 정지·회수한다.
  3. 완료·미완료·증거·재개 조건을 기록한다.
  4. 최종 보고를 한다.
  - 마무리 여유로 마지막 1시간은 신규 대형 태스크를 시작하지 않는다.
